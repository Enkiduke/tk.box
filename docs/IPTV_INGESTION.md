# Milestone 0 IPTV ingestion

This pass adds working source ingestion and durable metadata APIs to the existing single-process Fastify application. It does not enable provider media delivery. No provider credentials or real feed were available; fixture success does not prove provider, TLS, browser or IPTV playback compatibility.

## Storage and publication

Migration 2 creates `iptv_sources`, `iptv_channels`, `lineup_numbers`, `iptv_favorites`, `iptv_source_feeds` and `iptv_mappings`. Existing settings, sessions and schedule publications are retained. The earlier `SourceSnapshots` and pure reconciliation classes remain isolated experiments used by their original tests; application routes use `IptvStore` and `SourceRefresh`.

Each source stores encrypted endpoint configuration, the last validated snapshot and any held candidate. Channel provider metadata, including stream URLs, is encrypted separately with context-bound AES-GCM. API responses and audit records omit endpoint URLs, credentials, request headers, stream URLs and provider logo URLs. Source names and station/program titles are untrusted display text. Back up the database together with its protected encryption key; do not query or log decrypted endpoint objects.

An import parses and validates before beginning publication. A transaction reconciles channel state, reserves numbers, replaces the last-good snapshot, advances the source revision and records a sanitized audit event. Any transaction failure rolls back all of these changes. Expected revisions cover refresh publication, policy, endpoint edits, channel curation and feed binding. An edit during an active fetch causes the stale import to fail rather than overwrite the edit. Mapping approval has its own revision.

There is no approval step: channels list themselves by the source's listing rules (see **Channel listing** below). Listing is separate from presence and identity conflict. Missing channels disappear immediately from viewer listing, favorites and guide reads, while their ID, number, position, favorites, display-name override, listing override and mapping intent remain stored. An unambiguous return restores them without un-hiding a channel an administrator hid. `lineup_numbers` is the shared reservation table for future custom-channel admission too; the scheduler does not yet create numbered custom channels.

Each feed has a durable internal UUID, separate from its provider's `tvg-id` (a station/guide hint). Multiple HD, SD, alternate or backup feeds may share that hint and remain independently tunable and health-checked. Exact repeated entries (same guide ID, provider name, category and stream URI) are imported once. Different entries are retained even when their names or URLs match. Station grouping removes quality/backup tags but retains country, regional, language and time-shift differences; sharing a guide ID alone does not group stations.

Refreshes match feeds using unique combinations of accepted metadata, in order of evidence: exact entry, name plus URI, URI within a guide ID, name/category within a guide ID, and finally a unique guide ID. Matching requires uniqueness in both the complete old and incoming sets and never uses playlist order. URL rotation with a stable unique feed label, or a rename with a stable unique URI, keeps saved IDs and settings. Simultaneous name/URI changes and ambiguous matches require review; unmatched incoming entries involved in that ambiguity are held until resolved. Review shows sanitized incoming choices, accepts one into the saved record, or imports them as new feeds while retaining the old saved record as missing. Hidden state, favorites, numbers, manual mappings and other curation stay on their original UUID. This is metadata corroboration, not proof of broadcast content; uncertain signed-URL changes remain reviewable rather than stripping query parameters or guessing.

At startup, legacy guide-ID/name identities are upgraded transactionally from the last validated cached playlist. This restores alternate feeds that the old shared-ID quarantine collapsed, retains old UUIDs and curation, and leaves refresh success/due times unchanged. A normal playlist refresh also applies the new identity rules. No upstream request is needed for the upgrade.

## Fetch and completeness boundaries

- Metadata URLs must use HTTPS; HTTP requires explicit `allowInsecureHttp: true`. Userinfo and fragments are rejected. Query credentials are supported only inside encrypted endpoint state.
- Request headers are limited to Authorization, User-Agent, Referer and Accept. No Host, Cookie, proxy, forwarding or connection overrides. Additional provider requirements need explicit implementation and tests.
- Every hop resolves all DNS answers and rejects the request if any address is non-public. Native global unicast IPv6 is allowed with special/documentation/tunnel exclusions; IPv4-mapped IPv6, NAT64, local, private, link-local and reserved destinations are rejected. Connections pin a validated address through Node's lookup callback, retaining original Host and TLS identity. Socket pooling and environment proxies are disabled.
- At most three redirects, all within the source's approved origin. Each redirect repeats DNS validation. Cross-origin redirects require a deliberate endpoint change by the administrator; credentials are never forwarded to an unapproved origin.
- Requests have a 30-second overall deadline, 10-second socket inactivity timeout, 16 KiB header cap and 16 MiB compressed/decompressed body cap. Only complete HTTP 200 responses with consistent Content-Length, supported identity/gzip encoding and valid UTF-8 reach parsing. Partial, malformed, empty and oversized imports retain last-good data.
- A syntactically complete HTTP/M3U document can still be a logically truncated provider export. As an engineering safeguard, disappearance of **more than half** of at least two previously present, non-conflicted records is held as a suspicious candidate. Last-good lineup and success timestamp remain intact. An administrator can inspect sanitized incoming/missing records and accept the exact candidate using both its SHA-256 digest and current revision. A healthy replacement refresh clears the held candidate. Smaller logically incomplete exports cannot reliably be detected without provider-specific counts, markers or contracts; this remains a live validation risk. Empty imports are always rejected.

These rules apply to source **metadata**, not to HLS manifests, nested playlists, media segments, keys, logos or FFmpeg input. Those fetch paths remain disabled in the application until equivalent authorization, SSRF and processing controls are implemented.

## Refresh and guide behavior

Remote sources are due immediately after creation; persisted independent defaults are 12h for M3U and 6h for XMLTV. Intervals accept whole hours from 1 through 168. The application checks due work at startup and every 15 seconds. Scheduled and manual refreshes coalesce per source; at most four source fetches run globally. This registry assumes one application process, consistent with the native service design. Uploaded sources have no automatic due time and report `STATIC_SOURCE` for Refresh Now.

Failures retain the last success/snapshot and saved interval, with a sanitized diagnostic and next attempt at the saved cadence. HTTP 429/503 Retry-After is honored with a minimum one-minute backoff and maximum seven-day guard; next due never precedes either that backoff or the saved cadence. Manual refresh cannot bypass active provider backoff. There is no automatic in-request retry loop. Shutdown aborts active work and preserves its due time for the next process. Policy/endpoint edits win over stale fetch results.

An administrator adds an XMLTV URL directly to each M3U source. Each guide has its own refresh schedule. Existing linked guides remain available; editing a legacy shared guide through the source settings copies its cached listings and manual mappings to an individual guide before changing its settings. Exact guide IDs activate automatically when shared-ID feeds have compatible station names and the XMLTV ID is unique; unrelated stations sharing an ID need a manual match. Name suggestions remain inactive until approval. Mapping intent is scoped to channel/source/feed and retained even while its XML ID is missing or ambiguous; no automatic alternative replaces an invalid manual choice. Cached real intervals remain usable after feed refresh failure, with explicit null-program gaps after coverage ends. Feed fetch errors do not change channel visibility or call streaming teardown.

## Channel listing

Added October 18, 2026. There is no approval step. A channel is **listed** (in viewers' channel list, guide, favorites and tuning) when it is present, has no identity conflict, is not hidden by an administrator and meets its source's rules. `persistence/listing.ts` holds the rules as SQL predicates shared by every viewer read; migration 9 adds them.

- **Regular channels** are listed while they pass channel checks. With **Wait for a passing check** (on by default) a new channel stays unlisted until a check, or a viewer's relay, sees it play once; turn it off to list channels as soon as they are imported. Failing channels are hidden after two failed checks either way, unless **Hide channels that fail checks** is off.
- **Guide data (optional, per source).** With **Only list channels with guide data**, a regular channel is listed only while its mapped guide has a program airing now or starting within the look-ahead (default 2 hours; 0 means airing now). Placeholder titles ("No information", "To be announced", "Off air") do not count. Coverage is kept per channel as merged program intervals (`iptv_guide_coverage`), rebuilt when the guide or playlist is imported, the guide is linked or removed, or a match is changed. **Exceptions:** channels whose name or category contains an always-on keyword (default `24/7`, `24-7`, `24x7`, `247`, matched as whole words) and categories marked as not needing guide data are listed without listings.
- **Event channels** (categories that follow events, see **Sports events**) are listed while their event is live or starting soon. The check and guide rules do not apply to them.
- **Overrides.** Per channel, **Always list** skips every rule and **Hidden** is never listed; **Automatic** follows the rules. Up to 500 channels can be changed at once. Upgrading converts ignored or disabled channels to Hidden and channels exempted from checks to Always list.
- **Numbers.** Every present regular channel (and every always-listed event channel) holds a lineup number from import on, in playlist order, whether or not it is listed yet, so listing never reshuffles the lineup. Hidden and missing channels keep theirs. Other event channels take a number while their event is on.
- **Why not listed.** Administrators see each channel's state: Listed, Always listed, Waiting for a check, Failing checks, No guide data, No event on, Hidden, Identity conflict or Missing, with counts per state on the source overview.

`tests/listing.test.ts` covers the first-check rule, overrides, the guide rule with look-ahead, placeholders and always-on exceptions, mixed event and regular categories, and the upgrade from approval.

## Live playback

Added October 18, 2026. Listed channels play from the guide's ▶ button or the program dialog's **Watch live**.

- `POST /api/v1/live/sessions` `{channelId}` tunes the channel and answers once the first segment exists, with `{id, streamUrl, delivery, channel, source}`. `GET /api/v1/live/sessions/:id/index.m3u8` (full reauthorization) and `/seg-NNNNNN.ts` (local session check) serve a short sliding HLS window. `DELETE /api/v1/live/sessions/:id` releases it. Logout and shutdown stop all of a viewer's sessions; a session with no playlist or segment request for 45 seconds is dropped.
- `LiveTv` (`apps/server/src/services/live-tv.ts`) runs one FFmpeg relay per channel, shared by every viewer of that channel, so a provider connection limit is spent once per channel. At most eight relays and four sessions per viewer.
- Input is the channel's stored HLS or raw MPEG-TS URI with an HTTP(S)/TCP/TLS/crypto protocol allowlist. Raw TS reconnects in place; HLS is read in real time so a looping VOD playlist cannot outrun the window. H.264 4:2:0 video is copied (**Direct Stream**). Other video, such as MPEG-2 or HEVC, is encoded with libx264 (**Transcode**) under the same 1080p-or-lower rule and shared encoder permit as VOD. Audio is always AAC stereo, because browsers cannot decode the AC-3/MP2 common in IPTV. Interlaced sources are deinterlaced only when encoding.
- An upstream that drops after playback starts is restarted up to five times into the same window behind a discontinuity. The browser never receives the upstream URI. FFmpeg diagnostics are logged with URLs redacted.
- The web player prefers hls.js wherever Media Source Extensions exist. Chromium 141+ reports native HLS support, but its native player failed on these streams.

## Channel checks

Added October 18, 2026. Viewers only see channels that play. Each M3U source checks its present channels that are not hidden (ones that have played first) in the background, and channels that fail are left out of the channel list, guide, favorites and tuning. `apps/server/src/services/stream-probe.ts` holds the check; `ChannelHealth` (`services/channel-health.ts`) schedules it; `HealthStore` (`persistence/channel-health-store.ts`, migration 3) records results.

- **One connection per check.** A single FFmpeg run opens the stream the way the relay does (same protocol allowlist and user agent) and decodes about 7 seconds. HTTP status, DNS, refused, timeout and undecodable-data failures come from FFmpeg's own log, so no separate HTTP pre-check opens a second connection. This matters because providers that allow one connection often keep the slot busy for a few seconds after it closes. Detectors run on a 160-pixel copy (`freezedetect`, `silencedetect`) with one decoder thread. The same run writes a 64-bit difference hash of one frame and a 320-pixel JPEG for administrators. Audio-only (radio) inputs are retried once with only the detectors.
- **Offline screens.** A picture frozen for most of the sample *and* silent is a placeholder. A still picture **with** sound is kept, because it is usually a radio station. However, when three or more channels of a source freeze on the same informative picture, all of them are marked as the provider's offline screen, even with music. An administrator can also mark a captured picture as an offline screen (**Channels → Check → This is an offline screen**). Any channel showing a similar picture (Hamming distance ≤ 6) is then hidden immediately, including ones with animation or sound. Flat or black frames are never fingerprinted. HLS segments named like the usual placeholder files (`black.ts`, `blank.ts`, `placeholder.ts` and similar) also count.
- **No false removals.** A first failure only schedules a recheck 90 seconds later; a channel is hidden after two consecutive failures. Failures count only while some channel of the same source has played within 12 hours. A provider outage or an expired account therefore defers checks and never empties the lineup. Rate limits (429/458/509) and cancelled checks never count. One successful check, or a viewer's relay starting, restores a channel.
- **Max connections.** One server-wide limit (Settings → IPTV, default 1, up to 16) covers every source, viewer and check (`ProviderConnections`); the whole server also runs at most four checks at once. A connection counts as in use until its FFmpeg process has exited, so a channel switch waits briefly for the old stream to close. Viewers of the same channel share one connection. When a viewer tunes a channel on a source with no free connection, running checks on that source are cancelled (and retried a minute later) and the viewer waits for them to exit; no check starts while a viewer waits. Viewers never displace each other: once viewers hold every connection, a new channel is refused with `LIVE_CONNECTIONS_FULL`. A channel already playing for a viewer counts as working without a probe. A failed tune queues an immediate check of that channel.
- **Schedule.** Every channel is rechecked every 24 hours by default (0 means checks run only when requested), and newly imported channels are checked straight away. Due times are stored per channel, so a restart resumes where it stopped. Stream URIs and FFmpeg output never leave the server; results store only reason codes.
- **Overrides.** Per source, **Hide channels that fail checks** can be turned off. Per channel, **Always list** (channel Edit) exempts a false positive from every listing rule. **Forget offline screens** clears learned screens and rechecks the channels they hid.

## Channel logos

`GET /api/v1/iptv/channels/:id/logo` serves a cached image fetched server-side (public addresses only, PNG/JPEG/WebP/GIF, at most 1 MiB, never SVG). Order: an exact match in the community [tv-logo/tv-logos](https://github.com/tv-logo/tv-logos) repository, then the playlist `tvg-logo`, then the linked XMLTV channel `icon`. Library matching slugifies the provider name (region prefix such as `US:`, bracketed tags and HD markers removed, `+` becomes `plus`) and requires an exact `<slug>-<cc>.png` in that country, with the region taken from the name prefix or a `.cc` tvg-id suffix. The repository index is fetched from the GitHub API at most daily. Logos are fetched at runtime and are not vendored; that repository declares no license, and the marks belong to their owners.

## Sports events

Added October 18, 2026. Sports categories often list hundreds of event channels ("PPV 3: Canelo vs …") whose names stay up long after the event and are later reused. An M3U source can use sports events (**Settings → source → Sports → Use sports events for this source**, or **Sports events** when adding a source). Sports events apply per **category** (`group-title`): one playlist can mix event categories with regular stations. A category set to Automatic follows events when at least 40% of its names are matchups, dated listings or numbered event slots ("PPV 12", "Football Event 04"), or all of them for a category of two or three channels ("24/7" never counts as a date); a playlist without categories follows events as a whole. **Listing → Categories** sets a category to Regular or Event channels. A playlist with no recorded choice is detected automatically, on import and at startup: either the whole playlist (at least 20 channels and 20% event-like names) or any one category looks like events. The server log reports the measured share (`eventLikePercent`). An administrator's choice is never overridden. Event channels are then listed only from a lead time before a scheduled event (default 30 minutes) until 15 minutes after it ends. Regular categories and other sources are unaffected.

- **Schedules.** `SportsSchedule` (`services/sports-schedule.ts`) keeps a rolling schedule from yesterday through the day after tomorrow in `sports_events` (migration 5), and only fetches while some source uses sports events. ESPN's public scoreboard (`site.api.espn.com/apis/site/v2/sports/{sport}/{league}/scoreboard?dates=YYYYMMDD`, unofficial and undocumented; see [Public-ESPN-API](https://github.com/pseudo-r/Public-ESPN-API)) supplies every game of a day per league with live status: today's scoreboards are refreshed every 10 minutes, other days hourly. TheSportsDB's free v1 key (`123`, 30 requests a minute) supplies boxing and WWE: one next and one past event per league, plus up to three "Fighting" events per day, every 6 hours. Its other free calls return at most 3 events per day, so it is a supplement. Requests go through the restricted fetcher (public HTTPS only, size and time limits), are spaced out, and honor 429 Retry-After. A live event's end follows its status; otherwise a typical length per sport is assumed (`DURATION` in `providers/sports-feeds.ts`).
- **Matching.** `services/sports-match.ts` matches each channel's name (then group, then linked-guide listings) against those events: both teams by name, nickname or city; `HOU @ JAX` abbreviations; fighter surnames from "A vs. B"; numbered cards ("UFC 333"); titled shows with their league ("WWE Raw"). A date or time written in the name that contradicts the event rejects the match, which is what keeps recycled or old listings hidden. A name with its own date and time ("10/18 9:00 PM ET") but no known event gets a 3-hour window. Guide listings count too, except placeholder titles ("No Event", "Off Air", "SIGN OFF", "Next game: …", replays). A listing that names no known event counts only as a matchup ("A vs B") or as a league show while that league plays ("NFL Red Zone" on a Sunday); a team channel's listing with no game of that team on is filler. **Zones:** providers write each channel family's times in one unstated zone (here "Football Event 11ⓧ: … 11:30" is UK time and "FNTZ 06: … 11:15 AM" is Eastern). Each match pass learns the zone per family (the name before its slot number) from channels naming a scheduled kickoff, and applies it to that family's other channels; the server log lists learned zones. The window used is the current one, else the next; past windows mean the channel is hidden.
- **Visibility and checks.** Every minute, event channels whose event is live or starting soon take a number, and those whose event is over release it unless a viewer favorited them (audited as `sports_numbers_synced`). An event channel an administrator set to **Always list** keeps its number and stays listed; a hidden one is never listed. `sportsHidden` is one of the listing rules (`persistence/listing.ts`). Event channels are named by the event alone ("Bundesliga 09ⓧ: Borussia Monchengladbach vs. TSG Hoffenheim | Sunday, 18 October 2026 16:30" becomes "Borussia Monchengladbach vs. TSG Hoffenheim"; `eventChannelName`), unless an administrator set a display name. They stack by the event they carry (home, away and backup feeds share one row with selectable feeds, like other stacked channels), never by name; each feed is labelled by its provider slot and qualifier ("FNTZ 06", "Sportsnet+ 09", "NFL 02 · Away Stream"; `channelTag`). For a live sports event (not a guide-only match like "NFL Red Zone"), the guide shows the event as **Starting soon** from when the channel appears until kick-off, then the event, then blank slots (`blank: true` rows) instead of "No guide data". Channels matched by name or guide alone group by the matchup's two sides on the same UTC day (`stackKey` in `services/sports-match.ts`, stored per window), and the guide lists the event itself. Channel checks never sweep event channels: only those that are live or starting soon are checked (also for **Check all now**), once when they appear and again at the scheduled start, and retry a failing one every 10 minutes during the window. The usual two-failure confirmation, provider reachability rule and offline-screen detection still apply.
- **Configuration.** `SPORTS_ESPN_LEAGUES`, `SPORTS_TSDB_LEAGUES`, `SPORTS_NAME_TIMEZONE` (zone for names that give no zone); see `.env.example`. The TheSportsDB key is saved in Admin › Connections (TheSportsDB's free key is used until one is saved).

`tests/sports.test.ts` covers matching against ESPN- and TheSportsDB-shaped events, stale-listing rejection, name times and zones, guide listings, admission, visibility, guide events and check scheduling. Not yet verified against the provider's real channel naming; ESPN's API can change without notice.

**Sport icons.** An event channel with no logo of its own (library, playlist or guide icon) shows an icon for its sport instead of a monogram: soccer, American football, basketball, baseball, hockey, MMA, boxing, wrestling, golf, racing, tennis, cycling, rugby, cricket, darts, curling, or a trophy when the sport is unknown. The sport comes from the matched schedule event, else from the channel name, group, league and title (`sportOf` in `services/sports-match.ts`; "football" means soccer unless it is the NFL, college football or similar). Icons are original SVG line glyphs in `providers/sport-icons.ts`, served by the logo route with a 10-minute cache because a slot's next event can be another sport.
